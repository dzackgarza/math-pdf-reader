# M4 evidence: extraction plugins

Recorded on 2026-09-23 on the development workstation with the real providers.

## How an extraction runs

`plugins/manifests/extractions.json` lists the extraction plugins; the server reads it with `ExtractionManifestSchema` (src/contract/extraction.ts).
Each plugin is a command plus the PDF it accepts: `{"kind": "pdf", "limits": [...]}`, where a limit is `max_pages` or `max_bytes` and an empty list accepts any PDF.

| Plugin id | Command | Accepted PDF | Artifacts |
| --- | --- | --- | --- |
| `mineru-flash` | `bunx mineru-open-api@0.5.9 flash-extract $pdf --language en -o $output/extraction.md` | at most 20 pages and 10 MB (the vendor's flash limits) | Markdown |
| `mineru-precise` | `pdfbucket-mineru-precise $pdf $output https://mineru.net/api/v4` | any | Markdown, `content_list.json`, `layout.json` |
| `mistral-ocr` | `pdfbucket-mistral-ocr $pdf $output` | at most 50 MB (Mistral's per-request limit) | Markdown with a `<!-- page N -->` anchor per page |

The server runs a plugin (server/src/extractions.rs):

1. It refuses a PDF outside the plugin's limits before the plugin runs (`status: rejected`, with each violated limit and the observed value).

2. It substitutes `$pdf` (the stored `<root>/<key>.pdf`) and `$output` (an empty directory staged inside the root) into the command and runs it with the process environment, which carries `MINERU_API_TOKEN` and `MISTRAL_API_KEY`, and with the Python environment's bin directory first on PATH. The server never reads those variables.
   A plugin still running after `plugins.extraction_timeout_seconds` (pdf-bucket.config.json) is killed with its process group (`status: timed_out`).

3. On a non-zero exit it answers `status: failed` with the exit code and the plugin's stderr, and removes the staging directory: nothing reaches the root.

4. On exit 0 the plugin has written `$output/extraction.md` and optionally `$output/artifacts/`; a plugin that wrote anything else answers `502 plugin_contract_broken`. The store moves the previous `<root>/<key>.md` and `<root>/<key>.extraction/` to the desktop trash, then the artifacts to `<root>/<key>.extraction/` and the Markdown to `<root>/<key>.md` (last, so its presence marks a complete extraction), and the server answers `status: succeeded` with the path, SHA-256 and size of every placed file.

In the running app `<root>` is the data root, `$XDG_DATA_HOME/pdf-bucket`, so the artifacts sit beside the stored PDFs there.

The routes:

- `GET /api/plugins/extractions` lists the plugins with their accepted inputs.

- `POST /api/items/<key>/extractions/<plugin-id>` answers the outcome as JSON: 200 succeeded, 422 rejected, 502 failed, 504 timed out, 404 for an unknown item or plugin.
  The server sets Bun's `idleTimeout` to 0 because a provider run holds the request open for minutes.

MinerU precise splits a PDF into chunks of at most 200 pages (the live API's limit) and at most 4 MiB of average page bytes, extracts each chunk, and joins the results: the Markdown with a `<!-- pages a-b -->` header per chunk, `content_list.json` and `layout.json` with every `page_idx` shifted back to the whole document.

## Failing commands

A provider failure reaches the caller as the plugin's exit code and stderr, and the root keeps only the PDF:

```console
$ MINERU_API_TOKEN=not-a-token just extraction-evidence mineru-precise
{"status":"failed","key":"ten-page-notes","plugin_id":"mineru-precise","exit_code":1,"stderr":"Traceback (most recent call last): … pdfbucket_extractors.mineru_precise.MinerUError: HTTP 401 from mineru.net: {\"traceId\":\"3c706d554d64\",\"msgCode\":\"A0202\",\"msg\":\"user authenticate failed\",…}\n"}
$ ls -A <root>
ten-page-notes.pdf
```

The Mistral OCR run on the same fixture also failed: Mistral answered HTTP 402 `{"detail":"Check your subscription on https://admin.mistral.ai/subscription"}`, and the root again held only `ten-page-notes.pdf`.

## Mistral OCR against the documented API

The account used for these runs has no OCR subscription.
So the Mistral plugin is checked against Mistral's documentation ("Basic OCR", uploaded-PDF flow, in `mistralai/platform-docs-public`) and the installed SDK (`mistralai` 2.10.1), not against a live run:

| Step in `mistral_ocr.py` | Documented call | SDK 2.10.1 signature |
| --- | --- | --- |
| upload each chunk | `client.files.upload(file={"file_name", "content"}, purpose="ocr")` | `Files.upload(*, file, purpose: Literal['fine-tune', 'batch', 'ocr'], …)` |
| signed URL | `client.files.get_signed_url(file_id=…)` | `Files.get_signed_url(*, file_id, expiry=24, …)` |
| OCR | `client.ocr.process(model="mistral-ocr-latest", document={"type": "document_url", "document_url": signed_url.url})` | `Ocr.process(*, model, document, …) -> OCRResponse` |
| page anchors | `pages[].index` is 0-based (the first page of the documented response has `index: 0`), `pages[].markdown` holds the page's Markdown | `OCRPageObject` fields include `index` and `markdown` |
| limits | "Uploaded document files must not exceed 50 MB in size and should be no longer than 1,000 pages" | manifest `max_bytes` 50000000; `MAX_PAGES = 1000` per chunk |

The page anchor for a chunk that starts at whole-document page `s` (1-based) is `s + index`, so the anchors number pages 1 to N across chunks.
`page_ranges` and `split_pdf` build the chunks; `tests/test_extractors.py` tests them.

## Running an extraction from the inspector

The inspector's Extraction row lists the item's Markdown and artifacts, and under them the plugins from `GET /api/plugins/extractions` with a Run button.
Run calls `POST /api/items/<key>/extractions/<plugin-id>` and shows the answer:

| Answer | Inspector |
| --- | --- |
| request in flight | Run shows a spinner, the plugin list is locked, and a line says nothing is placed until the plugin finishes |
| 200 succeeded | the library reloads, so the Extraction row lists the placed Markdown and artifacts; the plugin name and the number of files written |
| 502 failed | the plugin's exit code, "nothing was written", and its stderr |
| 422 rejected | each violated limit with the observed value, e.g. "this PDF has 10 pages; the plugin accepts at most 5" |
| 404 | the server's `unknown_item` or `unknown_plugin` message |

Each item keeps the outcome of its last run while the window is open.

`just extract-screenshots` serves a two-PDF bucket whose extraction manifest lists the committed fixture extractor (`tests/fixtures/plugins/extractor.sh`) in three modes, so every run below is a real command run by the real runner, and no provider is called.
