# M4 evidence: extraction plugins

Recorded on 2026-09-23 on the development workstation with the real providers.

## How an extraction runs

`plugins/manifests/extractions.json` lists the extraction plugins in the manifest contract of `src/pdfbucket/manifest.py`. Each plugin is a command plus the PDF it accepts: `{"kind": "pdf", "limits": [...]}`, where a limit is `max_pages` or `max_bytes` and an empty list accepts any PDF.

| Plugin id | Command | Accepted PDF | Artifacts |
| --- | --- | --- | --- |
| `mineru-flash` | `bunx mineru-open-api@0.5.9 flash-extract $pdf --language en -o $output/extraction.md` | at most 20 pages and 10 MB (the vendor's flash limits) | Markdown |
| `mineru-precise` | `pdfbucket-mineru-precise $pdf $output` | any | Markdown, `content_list.json`, `layout.json` |
| `mistral-ocr` | `pdfbucket-mistral-ocr $pdf $output` | at most 50 MB (Mistral's per-request limit) | Markdown with a `<!-- page N -->` anchor per page |

`pdfbucket extract <root> <key> <manifest> <plugin-id>` is the runner:

1. It refuses a PDF outside the plugin's limits before the plugin runs (`status: rejected`, with each violated limit and the observed value).

2. It substitutes `$pdf` (the stored `<root>/<key>.pdf`) and `$output` (an empty directory staged inside the root) into the command and runs it with the process environment, which carries `MINERU_API_TOKEN` and `MISTRAL_API_KEY`. The runner and the server never read those variables.

3. On a non-zero exit it answers `status: failed` with the exit code and the plugin's stderr, and removes the staging directory: nothing reaches the root.

4. On exit 0 the plugin has written `$output/extraction.md` and optionally `$output/artifacts/`. The runner moves the artifacts to `<root>/<key>.extraction/` and the Markdown to `<root>/<key>.md` (last, so its presence marks a complete extraction), replacing any previous extraction of the item, and answers `status: succeeded` with the path, SHA-256 and size of every placed file.

The server exposes the runner:

- `GET /api/plugins/extractions` lists the plugins with their accepted inputs.

- `POST /api/items/<key>/extractions/<plugin-id>` answers the outcome as JSON: 200 succeeded, 422 rejected, 502 failed, 404 for an unknown item or plugin.
  The server sets Bun's `idleTimeout` to 0 because a provider run holds the request open for minutes.

MinerU precise splits a PDF into chunks of at most 200 pages (the live API's limit) and at most 4 MiB of average page bytes, extracts each chunk, and joins the results: the Markdown with a `<!-- pages a-b -->` header per chunk, `content_list.json` and `layout.json` with every `page_idx` shifted back to the whole document.

## Real provider runs

`just extraction-evidence <plugin-id> [fixture]` captures the fixture into a fresh root with `pdfbucket capture`, then runs `pdfbucket extract` with the shipped manifest.
The fixtures are built from the LaTeX beside them: `tests/fixtures/ten-page-notes.tex` (10 pages, SHA-256 `2cc26c66…d4d3b22`) and `tests/fixtures/long-notes.tex` (210 pages, SHA-256 `589452cb…f2bee`).

## Failing commands

A provider failure reaches the caller as the plugin's exit code and stderr, and the root keeps only the PDF:

```console
$ MINERU_API_TOKEN=not-a-token just extraction-evidence mineru-precise
{"status":"failed","key":"ten-page-notes","plugin_id":"mineru-precise","exit_code":1,"stderr":"Traceback (most recent call last): … pdfbucket_extractors.mineru_precise.MinerUError: HTTP 401 from mineru.net: {\"traceId\":\"3c706d554d64\",\"msgCode\":\"A0202\",\"msg\":\"user authenticate failed\",…}\n"}
$ ls -A <root>
ten-page-notes.pdf
```

The Mistral OCR run on the same fixture failed the same way: Mistral answered HTTP 402 `{"detail":"Check your subscription on https://admin.mistral.ai/subscription"}` to both the files API and OCR with an inline document, and the root again held only `ten-page-notes.pdf`. The Mistral OCR Markdown for the fixture is therefore not recorded here.
