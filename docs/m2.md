# M2 evidence: library UI over the bucket store

Recorded on 2026-09-24 on the development workstation (Arch Linux, WebKitGTK 2.52.6, Chromium 153 driven by Playwright).

## How the evidence is produced

```console
$ just library-screenshots
```

The recipe builds the web bundle, then `scripts/library_screenshots.py`:

1. makes three bucket roots in a temporary directory: an empty one; one holding `hand-copied.pdf`, a PDF with no embedded provenance; and one seeded with 1,000 PDFs by `scripts/seed_bucket.py`, which stores copies of the committed fixture PDFs in `tests/fixtures`, each under its own title, through `pdfbucket.store.store_pdf`, so each carries embedded provenance exactly as a capture does (nothing is downloaded);

2. serves each root with `src/server/serveBucket.ts` on a free port (never the configured 8770);

3. files the 300 most recent seeded items through the library API: six collections (two of them subcollections), four topics, seven tags, two notes, two saved searches;

4. lays the committed MinerU output (`tests/fixtures/mineru-ten-page-notes`) beside one item the way the extraction runner does, artifacts first and the Markdown last;

5. screenshots every state in the system Chromium, driven by Playwright, at 1600x1000, the mockups' size;

6. screenshots the library and the reader in the system WebKitGTK, the engine of the Tauri window, through `WebKitWebDriver` on a headless Weston display of 1400x900, the window's default size.

Playwright's own WebKit build is not used: its Linux build needs Ubuntu 24.04 libraries (ICU 74, `libxml2.so.2`, flite) that Arch does not ship.

## 1,000-item load and filter times

Seconds, from the run that produced the screenshots below (the seeded PDFs are copies of the four committed fixtures, 1 to 210 pages, 115 MB in all).

| Measurement | Seconds |
| --- | --- |
| Seed 1,000 PDFs through the store | 9.91 |
| `pdfbucket list` over 1,000 PDFs (one process) | 2.51 |
| `GET /api/library`, first request (index built from the files) | 2.61 |
| `GET /api/library`, second request (index cached, files re-stat'ed) | 0.016 |
| Window navigation to all 1,000 rows in the table | 0.51 |
| Typing a two-word filter until the table shows the matches | 0.078 |

The first request reads provenance out of every PDF; later requests re-read only PDFs whose modification time or size changed.
Filtering is the fzf filter over the item array in the browser; there is no search index.

- **Sidebar:** Library with its PDF count; Collections (with a new-collection button), Topics, Tags, Saved Searches; Settings.

- **Top bar:** a search field (Ctrl+F), Filters, Save search while a search is typed, Import URL (a PDF URL, or a page whose `citation_pdf_url` names its PDF; the server downloads it) and Add Folder (every PDF directly in a folder, with `file:` URLs as provenance; Browse opens the system folder chooser in the desktop window).

  Sources lists the PDF URL and the mirrors, each marked with its last check (serves the PDF, serves other bytes, serves nothing, not verified), a field to add a mirror, and Verify, which downloads each URL and compares its hash with the recorded original.
  The palette runs Verify All Sources and Rebuild Lost PDFs.

- **Status bar:** size on disk and the capture indicator.

- **Row context menu:** Open, Open in Browser, Add to Collection (existing or new), Add Tag…, Retrieve Metadata, Send to Zotero, Copy Link (source page, PDF), Show in Folder (desktop window), Delete… (the PDF moves to the desktop trash).
  The webview's own page menu is suppressed outside text fields and selections.

- **Filing:** collections, topics and tags are added through one combobox that picks an existing entry or creates one from the typed name.

### Reader (mockup 2)

`/read/<key>` is PDF.js at full width under a bar with Library, back, forward (Alt+← / Alt+→), the title and Copy link to this view.
Back and forward are PDF.js's own navigation history (`PDFHistory`): they move between the positions left by following links, outline entries and page jumps in the PDF, and do nothing past the first or last position, so they never leave the document.
PDF.js keeps no history in a frame; the page answers PDF.js's `webviewerloaded` event, sent to the embedding page before the viewer starts, by telling the viewer it is not embedded.
Library returns to the library view the window last showed, which the library keeps in session storage.
The address carries PDF.js's open parameters (`#page=…&zoom=…`), updated on every view change, so reloading or sharing the address reopens the same view.
Annotations made with PDF.js's tools (highlight, free text, ink, image, and the comment tool, which the reader turns on) are saved into the stored PDF: a short pause after a change, `PDFDocumentProxy.saveDocument()` writes the PDF as an incremental update and the page PUTs it to `/api/items/<key>/pdf`. The server keeps the new file only when it carries the provenance embedded in the stored one; the recorded original SHA-256 stays the hash of the captured bytes.
A failed save shows in the bar; PDF.js's leave-page warning stays on until every change is saved.
The page keeps M0's `citation_*` meta tags, with a `citation_author` tag per author.
A second after the page changes, the reader records the page and the page count as the item's last viewed page (`PUT /api/items/<key>/reading`, which leaves the item's modification time alone); an address without a fragment opens at that page.

## Item titles

An item title comes from the best source available, in this order:

| Source (`titleSource`) | Where it comes from |
| --- | --- |
| `resolver` | the BibTeX from the identifier resolver whose pattern accepts the source URL, the PDF URL or an identifier embedded in the PDF (`/arXivID`, `/DOI`, `prism:doi`); citation-js turns its LaTeX into text |
| `pdf-metadata` | the PDF's own `/Title`, else its XMP `dc:title` |
| `capture-hint` | the title the capture offered: link text or page title |
| `filename` | the stored file name |

A new capture runs the resolvers before the server answers.
A resolver title is written into the stored PDF (`/Title` and `dc:title`, with `/PDFBucketTitleSource` and the XMP `title-source` beside it), so the index still reads everything from the files.
The other sources are read from the file on every listing.
A resolver that fails or times out (20 s per upstream request) leaves the title to the next source, and the capture stands.

`POST /api/items/<key>/metadata` ("Retrieve metadata") runs the resolvers again and answers `{outcome, item}`: `outcome` is `resolved` (plugin, identifier, title), `unidentified`, or `failed` (plugin, identifier, message); `item` is the library item as it now stands.
A failed resolver keeps the title the item had.
An unknown key answers 404.

`tests/server-titles.test.ts` runs the real resolver commands against a replay of their captured upstream responses (`tests/fixtures/resolvers`): an arXiv capture offered the link text `View PDF` takes the arXiv title; a DOI capture takes `The sphere packing problem in dimension 8` from BibTeX that writes `$8$`; with the resolvers unreachable the titles fall back to the PDF's own title and to the hint; Retrieve metadata resolves such an item later.
