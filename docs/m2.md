# M2 evidence: library UI over the bucket store

Recorded on 2026-09-25 on the development workstation (Arch Linux, WebKitGTK 2.52.6, Chromium 153 driven by Playwright).

## How the evidence is produced

```console
$ just library-screenshots
```

The recipe builds the web bundle, then `scripts/library_screenshots.py`:

1. makes three bucket roots in a temporary directory: an empty one; one holding `hand-copied.pdf`, a PDF with no embedded provenance; and one seeded with 1,000 PDFs by `scripts/seed_bucket.py`, which stores copies of the committed fixture PDFs in `tests/fixtures`, each under its own title, with provenance embedded by `pdfbucket.provenance.embed_provenance` as a capture embeds it (nothing is downloaded);

2. serves each root with `pdf-bucket serve` (the app's server without its window) on a free port (never the configured 8770);

3. files the 300 most recent seeded items through the library API: six collections (two of them subcollections), four topics, seven tags, two notes, two saved searches;

4. lays the committed MinerU output (`tests/fixtures/mineru-ten-page-notes`) beside one item the way the extraction runner does, artifacts first and the Markdown last;

5. screenshots every state in the system Chromium, driven by Playwright, at 1600x1000, the mockups' size;

6. screenshots the library, the reader and a PDF's tab in the system WebKitGTK, the engine of the Tauri window, through `WebKitWebDriver` on a headless Weston display of 1400x900, the window's default size.

Playwright's own WebKit build is not used: its Linux build needs Ubuntu 24.04 libraries (ICU 74, `libxml2.so.2`, flite) that Arch does not ship.

## 1,000-item load and filter times

Seconds, from the run that produced the screenshots below (the seeded PDFs are copies of the four committed fixtures, 1 to 210 pages, 115 MB in all).

| Measurement | Seconds |
| --- | --- |
| Seed 1,000 PDFs through the store | 7.86 |
| `pdfbucket list` over 1,000 PDFs (one process) | 2.40 |
| `GET /api/library`, first request (index built from the files) | 2.72 |
| `GET /api/library`, second request (index cached, files re-stat'ed) | 0.036 |
| Window navigation to all 1,000 rows in the table | 0.65 |
| Typing a two-word filter until the table shows the matches | 0.15 |

The first request reads provenance out of every PDF; later requests re-read only PDFs whose modification time or size changed.
Filtering is the fzf filter over the item array in the browser; there is no search index.

### Library, populated (mockup 1)

![Populated library with an item selected](m2/library-populated.png)

- **Sidebar:** Library with its PDF count; Collections (with a new-collection button), Topics, Tags, Saved Searches; Settings.

- **Top bar:** a search field (Ctrl+F), Filters, Save search while a search is typed, Import URL (a PDF URL, or a page whose `citation_pdf_url` names its PDF; the server downloads it) and Add Folder (every PDF directly in a folder, with `file:` URLs as provenance; Browse opens the system folder chooser in the desktop window).
  A path that is not a directory answers 400 `not_a_folder`; when the `stat` call on the path fails for another reason (permission denied, a symlink loop, an I/O error), `POST /api/import-folder` answers 500 `folder_check_failed` with the operating system's error, and the library shows that error.

- **Library bar:** the quick filters with their counts, one at a time (a second click clears it): Unread (never opened, `#/unread`), Unfiled (in no collection, `#/unfiled`), Added This Week (`#/added-this-week`), Offline (`#/offline`), Needs Re-fetch (`#/needs-refetch`: items the index export holds whose PDF the store has lost, each with Rebuild, and Rebuild all); the Sort menu (any column, ascending or descending); List and Grid views (the choice is kept in the browser).
  The grid shows each PDF's first page, title, authors and reading progress; a double-click opens the reader in a tab.
  First pages are PNGs rendered by the store with MuPDF (PyMuPDF) at `/api/items/<key>/thumbnail?width=…`, cached under `$XDG_CACHE_HOME/pdf-bucket/thumbnails` and drawn again when the PDF is newer than its PNG. A key names no stored PDF only when `stat` on `<key>.pdf` finds no file (ENOENT, ENOTDIR, or something other than a file); when the `stat` call fails for another reason, every route on that key answers 500 `store_failed` with the operating system's error, so Forget never drops an item whose PDF may still be there.

- **Table:** title with PDF mark, authors (surnames; "et al." from three authors), last viewed page out of the page count ("Unread" for an item never opened), status (Cached, or Offline when the last check found the PDF URL dead or serving other bytes and no mirror serving the captured ones; the check shows on hover), source domain, date added, tag pills with an overflow count.
  Double-click or Enter opens the reader in a tab; Delete deletes.
  Each row (and each grid card) has a checkbox; with rows chosen, the selection bar adds a tag to all of them, files all of them into a collection (existing or new) through `POST /api/bulk/tags` and `/api/bulk/collections`, or clears the choice.

- **Inspector:** the title and authors; one line with the source page link, date added and size; Details (the first page, collections, topics, tags, sources, extraction) and Notes; Open and Send to Zotero.
  Sources lists the PDF URL and the mirrors, each marked with its last check (serves the PDF, serves other bytes, serves nothing, not verified), a field to add a mirror, and Verify, which downloads each URL and compares its hash with the recorded original.
  The palette runs Verify All Sources and Rebuild Lost PDFs.
  Related lists the PDFs sharing authors, collections, or topics and tags with the selected one, most shared first (an author counts three, a collection two, a tag one; a shared source domain only orders PDFs that share one of these), each with what it shares; a click selects it.

- **Status bar:** size on disk and the capture indicator.

- **Row context menu:** Open, Open in Browser, Add to Collection (existing or new), Add Tag…, Retrieve Metadata, Send to Zotero, Copy Link (source page, PDF), Show in Folder (desktop window), Delete… (the PDF moves to the desktop trash).
  The webview's own page menu is suppressed outside text fields and selections.

- **Filing:** collections, topics and tags are added through one combobox that picks an existing entry or creates one from the typed name.

### Tabs

The window is a row of tabs: the Library tab first, which never closes, then one tab per open PDF, in the order opened, each labelled with the PDF's title.
Double-click, Enter, Open in the row menu or the inspector, a Timeline title, and a capture from either browser each open the PDF's reader in a new tab, or show its tab when it is open.
Every tab stays loaded while another is shown, so a PDF keeps its page and zoom and the library keeps its view, selection and search.
Ctrl+Tab and Ctrl+Shift+Tab show the next and the previous tab, also from inside a PDF; Ctrl+W, the tab's close button or a middle click closes a PDF's tab, after the reader has reported its reading session and saved every pending annotation.
A PDF's external links open in the default browser (a new window in a browser tab), so the window keeps its tabs.
A PDF's tab counts as hidden for the reading session while another tab is shown.

### Reader (mockup 2)

`/read/<key>` is PDF.js at full width under a bar with Library, back, forward (Alt+← / Alt+→), the title and Copy link to this view.
The sidebar opens closed, whatever the PDF's `/PageMode` asks, unless the setting opens the outline (PDF.js's `sidebarViewOnLoad`, set before the viewer starts).
Back and forward are PDF.js's own navigation history (`PDFHistory`): they move between the positions left by following links, outline entries and page jumps in the PDF, and do nothing past the first or last position, so they never leave the document.
PDF.js keeps no history in a frame; the page answers PDF.js's `webviewerloaded` event, sent to the embedding page before the viewer starts, by telling the viewer it is not embedded.
On a reader page open on its own (a browser tab), Library returns to the library view the window last showed, which the library keeps in session storage; in the window's tab the Library link is hidden, since the tab row holds the Library tab.
The address carries PDF.js's open parameters (`#page=…&zoom=…`), updated on every view change, so reloading or sharing the address reopens the same view.
Annotations made with PDF.js's tools (highlight, free text, ink, image, and the comment tool, which the reader turns on) are saved into the stored PDF: a short pause after a change, `PDFDocumentProxy.saveDocument()` writes the PDF as an incremental update and the page PUTs it to `/api/items/<key>/pdf`. The server keeps the new file only when it carries the provenance embedded in the stored one; the recorded original SHA-256 stays the hash of the captured bytes.
A failed save shows in the bar; PDF.js's leave-page warning stays on until every change is saved.
The page keeps M0's `citation_*` meta tags, with a `citation_author` tag per author.
A second after the page changes, the reader records the page and the page count as the item's last viewed page (`PUT /api/items/<key>/reading`, which leaves the item's modification time alone); an address without a fragment opens at that page.

### Timeline

![Timeline](m2/timeline.png)

While a PDF is open, the reader keeps a reading session: when it opened, the last moment it was read, and each page read, with its seconds.
A page counts only in stretches of at least 5 seconds (a page scrolled past or jumped over does not); a stretch ends when the page changes, when the reader is hidden, or 10 minutes after the last pointer, wheel or key input, and counting resumes with the next input.
The reader reports the session every 30 seconds, on each page change and as a beacon when the page is left (`POST /api/reading-sessions`, stored by session id in `<root>/reading-sessions.json` with the item's title, authors, year, abstract and source page as they were, so an entry outlives the item); nothing is sent until a page is read.
The sessions only describe the past: the item keeps its last viewed page as before.

The Timeline shows them newest first as daisyUI's vertical timeline with the icon snapped to the start: sessions of one PDF opened within half an hour of the last reading form one entry, and an entry read for less than the Shortest reading setting (30 seconds by default) is hidden.
Each entry gives the time, the title (a link to the reader, or to the source page once the PDF has left the bucket), authors and year, the time read and the pages read, and the abstract when a resolver gave one (arXiv's API for arXiv papers).

### Theme

Theme is Match the system (the default), Light or Dark.
Match the system follows the system's light or dark setting (`prefers-color-scheme`) and changes with it; Light and Dark hold whatever the system says.
The library and the reader page take their colours from `light-dark()` pairs under the root's `color-scheme`, and the PDF.js viewer takes the same choice (its `viewerCssTheme` option).
PDF pages keep their own colours.
The desktop window's WebKitGTK reads the system setting from GTK, which on Wayland follows the desktop's `org.gnome.desktop.interface color-scheme`.

## Item titles

An item title comes from the best source available, in this order:

| Source (`titleSource`) | Where it comes from |
| --- | --- |
| `resolver` | the BibTeX from the identifier resolver whose pattern accepts the source URL, the PDF URL or an identifier embedded in the PDF (`/arXivID`, `/DOI`, `prism:doi`); citation-js turns its LaTeX into text |
| `pdf-metadata` | the PDF's own `/Title`, else its XMP `dc:title` |
| `capture-hint` | the title the capture offered: link text or page title |
| `filename` | the stored file name |

A new capture runs the resolvers before the server answers.
A resolver title is written into the stored PDF (`/Title` and `dc:title`, with `/PDFBucketTitleSource` and the XMP `title-source` beside it), so the index still reads everything from the files.
The other sources are read from the file on every listing.
A resolver that fails or times out (20 s per upstream request) leaves the title to the next source, and the capture stands.

`POST /api/items/<key>/metadata` ("Retrieve metadata") runs the resolvers again and answers `{outcome, item}`: `outcome` is `resolved` (plugin, identifier, title), `unidentified`, or `failed` (plugin, identifier, message); `item` is the library item as it now stands.
A failed resolver keeps the title the item had.
An unknown key answers 404.

`tests/server-titles.test.ts` runs the real resolver commands against a replay of their captured upstream responses (`tests/fixtures/resolvers`): an arXiv capture offered the link text `View PDF` takes the arXiv title; a DOI capture takes `The sphere packing problem in dimension 8` from BibTeX that writes `$8$`; with the resolvers unreachable the titles fall back to the PDF's own title and to the hint; Retrieve metadata resolves such an item later.

## Mockup elements not reproduced

Each has no home in the reused components or in PDF.js, or belongs to a later milestone; none is drawn as a control that does nothing.
The roadmap card's Decision Log records them.

| Mockup | Element | Why it is absent |
| --- | --- | --- |
| 1 | Offline Cache view | Every stored item is a local file, so it would equal Library. |
| 1, 4 | Chrome and Firefox toggles, browser capture panel | Each extension's toolbar popup holds its capture switch (M1); the status bar shows whether captures can land. |
| 2 | Provenance panel beside the reader | The reader is for reading; the source page and PDF links are in the inspector and the row menu, and the rest travels inside the PDF. |

| 2 | Collection list column beside the reader | Each PDF is its own tab after the Library tab. |

| 4 | Research jumping-off points panel | A planning checklist, not an app function. |
