# M3 evidence: send to Zotero

Recorded on 2026-09-24 (UTC 2026-09-23) on the development workstation against the user's Zotero library (Zotero 8 with the local write API addon 3.4.0 on port 23119).

## How a send runs

`POST /api/items/<key>/zotero` on the bucket server:

1. `pdfbucket resolve <root> <key> plugins/manifests/resolvers.json` lists the item's identifier candidates in order: the source URL, the PDF URL, then the identifiers embedded in the PDF (`/arXivID` and `/DOI` in the document information dictionary, which arXiv's generated PDFs carry; `prism:doi` and `prism:isbn` in XMP). The first candidate that a plugin's identifier pattern accepts goes to that plugin on stdin; the plugin prints one BibTeX entry.

2. With no accepted candidate, the entry is `@unpublished` (Zotero's manuscript type) carrying only the title hint.
   No other field is written.

3. `import_bibtex` creates the item in the library root, except for an arXiv identifier: Zotero's BibTeX import maps `@misc` to `document` and maps no entry type to `preprint`, so an arXiv item is created with `import_by_identifier` on `arXiv:<id>`, Zotero's own arXiv translator (the arxiv resolver has already confirmed the id against arXiv).
   The bucket records the Zotero key in `organization.json` at once, then each later step as it lands:

| Step | Write API call | What it writes |
| --- | --- | --- |
| `fields` | `update_item_fields` | `url` = the capture's source URL, `accessDate` = the capture time |
| `pdf` | `POST /attach` with the stored bytes, unless the item already has a stored PDF attachment whose file hashes to the capture's original SHA-256 | the stored PDF (provenance embedded), title "Full Text PDF"; or nothing, recording Zotero's own copy of the same bytes (the PDF an identifier import downloads) |
| `markdown` | `POST /attach` with the bytes of `<key>.md` | the extraction Markdown as `<ZoteroKey>_extracted.md`, the name the extraction loop's completion criterion looks for |

4. A send on an item with no step owed answers `409 already_sent` with the Zotero key and never contacts Zotero.
   A send that failed part way, or an extraction made after the send, leaves steps owed; the next send performs only those, on the same Zotero item.

5. A send that completes every owed step removes the item from the bucket: `pdfbucket remove` moves the PDF, the Markdown and the artifact directory to the desktop trash, and the filing is dropped.
   `DELETE /api/items/<key>` removes any item the same way without a send.

Resolver failures answer `502 resolver_failed` with the plugin's exit code and last stderr line; a Zotero that refuses or does not answer gives `502 zotero_failed`.

Send to Zotero is in the inspector, the row context menu and the command palette ("Send Selected PDF to Zotero"). A failed or refused send shows its reason in the inspector.

## Resolver plugins

`plugins/manifests/resolvers.json`, in the manifest contract of `src/pdfbucket/manifest.py`. Each command runs in the manifest's directory with the upstream base URL as its argument.

| Plugin | Accepts | Upstream | Output |
| --- | --- | --- | --- |
| `doi` | a DOI or `doi.org` URL | `https://doi.org/<doi>` with `Accept: application/x-bibtex` | the registration agency's BibTeX |
| `isbn` | an ISBN | Open Library `/isbn/<isbn>.json` and `/authors/<key>.json` | `@book` built with citation-js |
| `arxiv` | an arXiv id or an `arxiv.org/abs/` or `/pdf/` URL | `https://arxiv.org/bibtex/<id>` | arXiv's BibTeX, with `archivePrefix`/`primaryClass` renamed to their biblatex names `eprinttype`/`eprintclass` |
| `zbmath` | a Zbl number or `zbmath.org/?q=an:` URL | zbMATH Open `/v1/document/_search` | `@article` built with citation-js |

`tests/test_resolution.py` runs `pdfbucket resolve` and each real plugin against a local server that replays the upstream responses captured on 2026-09-23 (`tests/fixtures/resolvers/captures.json` names each live URL).

## Evidence run

Two PDFs, captured into a fresh root (`XDG_DATA_HOME=$(mktemp -d)`) and served by `src/server/serveBucket.ts` on a free port with the real Zotero URL:

```console
$ uv run pdfbucket capture $root tests/fixtures/arxiv-2609.21174v1.pdf 2609.21174v1 \
    https://arxiv.org/pdf/2609.21174v1 https://arxiv.org/abs/2609.21174v1 "On The Cyclicity of Algebraic Lattices"
$ uv run pdfbucket capture $root tests/fixtures/lecture-notes.pdf lecture-notes.pdf \
    https://www.math.example.edu/~author/lecture-notes.pdf https://www.math.example.edu/~author/teaching.html "Lattices and Quadratic Forms"
$ uv run pdfbucket extract $root lecture-notes plugins/manifests/extractions.json mineru-flash
$ bun src/server/serveBucket.ts $root http://127.0.0.1:23119
```

### arXiv send through Zotero's identifier import

The run above created the arXiv item through `import_bibtex`, and it arrived as `document`: Zotero's BibTeX translator maps `@misc` to `document` and has no mapping to `preprint` for any entry type.
The send now creates arXiv items with `import_by_identifier`. Rerun on 2026-09-23 over a fresh root with the same fixture (top-level count 1929 before):
