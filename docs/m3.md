# M3 evidence: send to Zotero

Recorded on 2026-09-24 (UTC 2026-09-23) on the development workstation against the user's Zotero library (Zotero 8 with the local write API addon 3.4.0 on port 23119).

## How a send runs

`POST /api/items/<key>/zotero` on the bucket server:

1. `pdfbucket resolve <root> <key> plugins/manifests/resolvers.json` lists the item's identifier candidates in order: the source URL, the PDF URL, then the identifiers embedded in the PDF (`/arXivID` and `/DOI` in the document information dictionary, which arXiv's generated PDFs carry; `prism:doi` and `prism:isbn` in XMP). The first candidate that a plugin's identifier pattern accepts goes to that plugin on stdin; the plugin prints one BibTeX entry.

2. With no accepted candidate, the entry is `@unpublished` (Zotero's manuscript type) carrying only the title hint. No other field is written.

3. `import_bibtex` creates the item in the library root. The bucket records the Zotero key in `organization.json` at once, then each later step as it lands:

   | Step | Write API call | What it writes |
   | --- | --- | --- |
   | `fields` | `update_item_fields` | `url` = the capture's source URL, `accessDate` = the capture time |
   | `pdf` | `POST /attach` with the stored bytes | the stored PDF (provenance embedded), title "Full Text PDF" |
   | `markdown` | `POST /attach` with the bytes of `<key>.md` | the extraction Markdown as `<ZoteroKey>_extracted.md`, the name the extraction loop's completion criterion looks for |

4. A send on an item with no step owed answers `409 already_sent` with the Zotero key and never contacts Zotero. A send that failed part way, or an extraction made after the send, leaves steps owed; the next send performs only those, on the same Zotero item.

5. `DELETE /api/items/<key>` moves a sent item's PDF, Markdown and artifact directory to the desktop trash (`pdfbucket remove`, send2trash). An item whose PDF has not reached Zotero answers `409 not_sent`. Nothing removes an item automatically.

Resolver failures answer `502 resolver_failed` with the plugin's exit code and last stderr line; a Zotero that refuses or does not answer gives `502 zotero_failed`.

The inspector shows the item's Zotero key, send date and metadata source, and carries Send to Zotero and, once sent, Remove from bucket; the command palette has "Send selected PDF to Zotero".

## Resolver plugins

`plugins/manifests/resolvers.json`, in the manifest contract of `src/pdfbucket/manifest.py`. Each command runs in the manifest's directory with the upstream base URL as its argument.

| Plugin | Accepts | Upstream | Output |
| --- | --- | --- | --- |
| `doi` | a DOI or `doi.org` URL | `https://doi.org/<doi>` with `Accept: application/x-bibtex` | the registration agency's BibTeX |
| `isbn` | an ISBN | Open Library `/isbn/<isbn>.json` and `/authors/<key>.json` | `@book` built with citation-js |
| `arxiv` | an arXiv id or an `arxiv.org/abs/` or `/pdf/` URL | `https://arxiv.org/bibtex/<id>` | arXiv's BibTeX, with `archivePrefix`/`primaryClass` renamed to their biblatex names `eprinttype`/`eprintclass` |
| `zbmath` | a Zbl number or `zbmath.org/?q=an:` URL | zbMATH Open `/v1/document/_search` | `@article` built with citation-js |

`tests/test_resolution.py` runs `pdfbucket resolve` and each real plugin against a local server that replays the upstream responses captured on 2026-09-23 (`tests/fixtures/resolvers/captures.json` names each live URL).

### Item type of an arXiv send

The arXiv item arrives as `document`, not Zotero's `preprint`. `import_bibtex` runs Zotero's BibTeX translator, which maps `@misc` to `document` and has no mapping to `preprint` for any entry type; it keeps the arXiv id only as `arXiv: <id>` in Extra, and only when the entry names it with biblatex's `eprinttype`. A `preprint` needs either a type change after the import (the write API's `replace_item_json`) or Zotero's own arXiv translator through `import_by_identifier`; neither is part of the planned send path.
