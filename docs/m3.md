# M3 evidence: send to Zotero

Recorded on 2026-09-24 (UTC 2026-09-23) on the development workstation against the user's Zotero library (Zotero 8 with the local write API addon 3.4.0 on port 23119).

## How a send runs

`POST /api/items/<key>/zotero` on the bucket server:

1. `pdfbucket resolve <root> <key> plugins/manifests/resolvers.json` lists the item's identifier candidates in order: the source URL, the PDF URL, then the identifiers embedded in the PDF (`/arXivID` and `/DOI` in the document information dictionary, which arXiv's generated PDFs carry; `prism:doi` and `prism:isbn` in XMP). The first candidate that a plugin's identifier pattern accepts goes to that plugin on stdin; the plugin prints one BibTeX entry.

2. With no accepted candidate, the entry is `@unpublished` (Zotero's manuscript type) carrying the item's title as the library shows it and the page URL (below).
   No other field is written.

3. Before importing, the send looks for the item in Zotero: a top-level item (not in the trash) whose DOI is the resolver entry's DOI, or whose URL is the page URL, found with the local API's `qmode=everything` search on `/api/users/0/items/top` and compared field by field.
   A match (the earliest added, when there are several) is the send's item and the response says `created: false`; this covers a send Zotero finished that the bucket never recorded, and a work the library already holds.
   The page URL is the capture's source URL, or its PDF URL when the capture has no linking page.

4. With no match, `import_bibtex` creates the item in the library root, except for an arXiv identifier: Zotero's BibTeX import maps `@misc` to `document` and maps no entry type to `preprint`, so an arXiv item is created with `import_by_identifier` on `arXiv:<id>`, Zotero's own arXiv translator (the arxiv resolver has already confirmed the id against arXiv).
   The bucket records the Zotero key in `organization.json` at once, then each later step as it lands:

| Step | Write API call | What it writes |
| --- | --- | --- |
| `fields` | `update_item_fields` | `url` = the page URL, `accessDate` = the capture time |
| `pdf` | `POST /attach` with the stored bytes | the bucket's stored PDF, with the reader's annotations and the embedded provenance, title "Full Text PDF"; attached even when Zotero's import downloaded a PDF of its own |
| `markdown` | `POST /attach` with the bytes of `<key>.md` | the extraction Markdown as `<ZoteroKey>_extracted.md`, the name the extraction loop's completion criterion looks for |
| `notes` | `attach_note`, once per note | each of the item's notes as a child note: the text HTML-escaped, a blank line starting a paragraph and a line break kept as `<br/>` (the paragraph rules of Zotero's `text2html`) |

5. A send on an item with no step owed answers `409 already_sent` with the Zotero key and never contacts Zotero.
   A send that failed part way, or an extraction or note made after the send, leaves steps owed; the next send performs only those, on the same Zotero item.
   The send runs as a task of its own, so a client that disconnects mid-send does not stop it recording each step; sends of one item run one at a time, sends of different items side by side.

6. A send that completes every owed step removes the item from the bucket: `pdfbucket remove` moves the PDF, the Markdown and the artifact directory to the desktop trash, and the filing is dropped.
   `DELETE /api/items/<key>` removes any item the same way without a send.

Resolver failures answer `502 resolver_failed` with the plugin's exit code and last stderr line; a Zotero that refuses, answers with an error status or a body that is not the write API's JSON (Zotero without the addon answers `404 No endpoint found` in plain text), or does not answer within its timeouts (5 s to connect, 180 s per request) gives `502 zotero_failed`.

Like every state-changing route, the send only runs for the bucket's own pages, the capture extension, or a client that is not a browser (`server/src/guard.rs`, Go's `CrossOriginProtection` rules on `Sec-Fetch-Site` and `Origin`): a web page on another site that POSTs to `/api/items/<key>/zotero` gets `403 cross_origin_request`, and a request body in a type its route does not read gets `415 unsupported_media_type`.

Send to Zotero is in the inspector, the row context menu and the command palette ("Send Selected PDF to Zotero"). A failed or refused send shows its reason in the inspector.

## Resolver plugins

`plugins/manifests/resolvers.json`, in the manifest contract of `src/pdfbucket/manifest.py`. Each command runs in the manifest's directory with the upstream base URL as its argument.

| Plugin | Accepts | Upstream | Output |
| --- | --- | --- | --- |
| `doi` | a DOI or `doi.org` URL | `https://doi.org/<doi>` with `Accept: application/x-bibtex` | the registration agency's BibTeX |
| `isbn` | an ISBN | Open Library `/isbn/<isbn>.json` and `/authors/<key>.json` | `@book` built with citation-js |
| `arxiv` | an arXiv id or an `arxiv.org/abs/` or `/pdf/` URL | `https://arxiv.org/bibtex/<id>` | arXiv's BibTeX, with `archivePrefix`/`primaryClass` renamed to their biblatex names `eprinttype`/`eprintclass` |
| `zbmath` | a Zbl number or `zbmath.org/?q=an:` URL | zbMATH Open `/v1/document/_search` | `@article` built with citation-js |

`tests/test_resolution.py` runs `pdfbucket resolve` and each real plugin against a local server that replays the upstream responses captured on 2026-09-23 (`tests/fixtures/resolvers/captures.json` names each live URL).
