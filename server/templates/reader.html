{# Runs in the reader page. The viewer is same-origin, so the page reads PDF.js's event bus. Back and forward are PDF.js's PDFHistory: the positions left by following links, outline entries and page jumps in this PDF. PDFHistory.back and forward do nothing at either end, so they never leave the document. The frame's history state (History API) carries PDFHistory's position number, `uid`: a popstate moves to an older or newer one; any other change of it is a new position, which drops the newer ones. The buttons are enabled from that record. Every view change (page, zoom, scroll) replaces the address's fragment with PDF.js's own open parameters. The fragment the page was opened with goes to the viewer as a same-document replace, which PDF.js's hashchange handler applies (as the initial view if the document is still loading) and which adds no history entry. An address without a fragment opens at the page last viewed. Reading: a second after the page changes, the page and the page count go to /api/items//reading, which records them as the item's last viewed page. Reading stops counting after data-idle-minutes without input (pointer, wheel, key). Reading session: a stretch on one page counts once it lasts data-min-page-seconds; it ends when the page changes, when the page is hidden, or data-idle-minutes after the last input (pointer, wheel, key), and a new one starts with the next input. The session (opening time, last moment read, seconds per page) goes to /api/reading-sessions every 30 seconds, on each page change, and as a beacon when the page is left; nothing is sent until a page is read. Saving (RFC 9110 conditional requests): the page keeps the SHA-256 of the bytes the viewer loaded, the stored PDF's entity tag. The annotation storage reports its first change after each save (onSetModified, wrapped so PDF.js's own callback still runs); a short pause later, PDFDocumentProxy.saveDocument writes the PDF with every annotation as an incremental update of the loaded bytes, and the page PUTs it with `If-Match` naming them. The server keeps it while the stored file still holds those bytes and the new ones carry the item's provenance, and answers the new entity tag. Saves run one after another; a failed save shows the server's message and leaves later saves to run. When the stored PDF changed since it was loaded (412), the page keeps its bytes as the user's copy, reloads the stored PDF, and shows the conflict: the user's copy can be shown, saved over the stored PDF, or discarded. The page's state: `failure` (the last save's error text, until a save succeeds) and `mine` (the user's copy while a conflict is open). window.readerControl.settle sends the reading session, runs any pending save and waits for every save; it rejects while a save has failed or a conflict is open. The Library link and a closing tab wait for it and stay when it rejects. In a library tab the tab strip holds the Library tab, so the page hides its Library link. Once the viewer is up the page dispatches `reader-ready` on its frame element; the tab strip then reads window.readerControl. A frame's document stays visible while its tab is hidden: the page counts as hidden when its frame is invisible, and the tab strip dispatches `visibilitychange` on it at each switch. The page passes its focus to the viewer, so a shown tab scrolls with the keyboard. #}
